# AGENTS.md

## Mission

Implement Book2Epub exactly as specified in this repository. The product converts cleaned page images of technical books into a **reflowable EPUB 3.3** with semantic text, headings, code, formulas, tables, figures, captions, lists, notes, and source-page navigation reconstructed from MinerU `middle.json`.

## Mandatory operating rules

1. **Do not enter or request Plan mode.** The milestone specifications are the implementation plan. Start implementation directly from the current milestone.
2. **Do not perform web research to decide architecture, dependencies, schemas, or standards.** Required external facts are frozen in the specification and appendices. If an upstream behavior differs from the frozen contract, fail loudly and report the incompatibility instead of silently redesigning.
3. **Windows native only.** Do not introduce WSL, Docker, Linux-only commands, bash scripts as required paths, or a remote execution dependency.
4. **Use `uv`.** Python is 3.12. Do not replace `uv` with Poetry, Conda, Pipenv, or a custom environment manager.
5. **Pin MinerU to 3.4.5.** Do not upgrade to MinerU 4 alpha/pre-release or another stable version without a human-approved contract change.
6. **The sole MinerU source of truth is `*_middle.json`.** Production conversion MUST NOT read MinerU Markdown, `content_list.json`, or `content_list_v2.json`.
7. **The normal MinerU backend is `hybrid-engine` with `--effort high`, OCR mode, formulas enabled, tables enabled, and image analysis enabled.** No HTTP-client backend is permitted.
8. **The primary output is reflowable EPUB 3.3.** Do not implement fixed-layout EPUB as the production output.
9. **Never use a whole scanned page image as an EPUB page or background.** Never create transparent OCR overlays or absolute-positioned replicas of source pages.
10. **Do not use Pandoc in the production conversion path.** EPUB XHTML, package metadata, navigation, container files, and ZIP packaging are generated by Book2Epub itself.
11. **Preserve provenance.** Every BookIR block derived from MinerU must retain source page, source bbox, original MinerU block type, and a stable source identifier when available.
12. **Do not silently discard unsupported data.** Unknown MinerU block/span fields must be retained in `extensions`/raw provenance and reported. Unknown block types become explicit `UnknownBlock` IR nodes or a validation error according to the milestone contract.
13. **Do not invent content.** Do not use an LLM to rewrite OCR, infer missing prose, repair formulas semantically, translate text, or generate captions. Deterministic normalization only.
14. **Do not trade semantic fidelity for visual imitation.** bbox is used to infer relative intent (order, alignment, size class, relationships), never to recreate page coordinates in EPUB.
15. **No JavaScript in generated EPUB.** No runtime web app behavior, MathJax, client-side layout scripts, or online resources.
16. **No network dependency during normal conversion.** After MinerU models and EPUBCheck are installed, `convert` must work offline. MinerU must run with local models.
17. **No TODO implementations, stubs, fake-success paths, or tests that assert only that code ran.** Tests must verify structural output.
18. **Do not weaken validation.** EPUBCheck errors are fatal. Warnings are recorded and fail the release gate when they originate from generated markup under our control.

## Governing-document precedence

When requirements conflict, use this order:

1. `AGENTS.md`
2. `00_PRODUCT_AND_ARCHITECTURE.md`
3. the current milestone file
4. appendices referenced by that milestone
5. existing source code/tests only after the above

If two governing files genuinely conflict, stop implementation at that conflict and report the exact sections. Do not choose a policy yourself.

## Required implementation order

Implement milestones in numeric order: M0 -> M1 -> M2 -> M3 -> M4 -> M5.

Do not skip ahead to produce a superficially working EPUB. In particular, do not bypass BookIR by directly translating MinerU JSON into XHTML.

At the end of each milestone:

```powershell
uv run ruff check .
uv run pytest -q
uv run mypy src/book2epub
```

If any command fails, the milestone is not complete.

## Repository conventions

- Source root: `src/book2epub/`
- Tests: `tests/`
- Integration fixtures: `tests/fixtures/`
- Tool downloads local to repo: `.tools/`
- Per-conversion working data: `.work/jobs/<job-id>/`
- Generated user output: only where explicitly requested by CLI
- Text files: UTF-8, LF in repository; code must tolerate Windows paths and CRLF source text
- All public filesystem APIs use `pathlib.Path`
- No hard-coded drive letters or user-profile paths
- No shell string construction for subprocess arguments; pass argument arrays

## Core quality priorities

In descending order:

1. correct semantic reading order;
2. no loss of prose/code/math/table/figure content available in `middle.json`;
3. correct heading hierarchy and navigation;
4. ordinary EPUB-reader compatibility;
5. formula and table semantics;
6. source-layout intent (relative width, alignment, sidebar/figure relationships);
7. visual polish;
8. speed.

Performance optimizations must never change semantics without an explicit compatibility test.

## Forbidden shortcuts

Do not:

- convert MinerU Markdown to EPUB;
- convert `content_list_v2` to EPUB because it is easier;
- rasterize formulas that successfully convert to MathML;
- rasterize tables when valid table HTML exists;
- replace code blocks with screenshots;
- place everything into one XHTML file without chapter/size splitting;
- ignore EPUBCheck;
- drop headers/footers/page numbers before using them for source-page reconstruction logic;
- infer a code programming language when MinerU does not provide one unless a later explicit requirement adds a deterministic classifier;
- create `position:absolute`, fixed page dimensions, CSS columns, or a page background image to mimic print layout.

## Change discipline

Architecture changes require a human-approved specification change. If implementation reveals an upstream mismatch, add a concise note to `docs/upstream-mismatches.md` with:

- current milestone;
- observed behavior;
- expected frozen behavior;
- minimal reproduction command;
- actual versions;
- whether work can continue without changing the contract.

Do not redesign around the mismatch unless the existing specification already defines a fallback.
